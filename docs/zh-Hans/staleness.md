# 防止笔记悄悄变成过时的

[English](../en/staleness.md) · [한국어](../ko/staleness.md) · [日本語](../ja/staleness.md) · **简体中文** · [Español](../es/staleness.md) · [Français](../fr/staleness.md)

最有用的笔记，是那些能说清楚某件事怎么工作的——哪个文件调用哪个函数，顺序怎么样。但这类笔记也最容易过时，因为代码一直在改，笔记却不动。

问题不在于笔记本身变旧。问题是，一篇旧笔记看起来跟新笔记一模一样，AI 读了就相信了，凭着早就过时的信息做决定。这比根本没有笔记还要糟糕。

`llmw` 没有尝试猜测哪些笔记过时了——原因见最后的 [为什么它不干脆直接检查代码](#为什么它不干脆直接检查代码)。它用的是三种更简单的办法。

## 1. 搜索和读取会告诉你笔记的信息有多旧

查找结果现在会显示笔记的标题和上次更新的时间：

```
1. wiki/decisions/retry-budget.md
   title: Retry budget moves into the uploader (v0.1.18)
   updated: 2026-07-13 (49d ago)
   summary: ...
```

如果 `llmw` 看到笔记的本文在笔记声称的日期之后有过改动，你会看到两个时间：

```
   updated: 2026-07-13 (49d ago, body changed 2026-08-31)
```

这个差异说明有人改过笔记说的话但没更新日期——所以笔记可能讲的是比它说的更新的东西，也可能更旧。同时显示两个数字是故意的：只显示一个的话，就会悄悄把"上次有人改过这个"变成"上次有人检查过这个还是不是真的"，这两个含义是完全不一样的。

**是本文，不是文件。** 把笔记标记为已取代、加一个 `code:` 列表、或修改一个标签，会重写文件但笔记说的话一个字都不变 — 而且你被告诉那些情况下*不要*动日期。早期版本是比较文件时间戳的，这个项目自己的 wiki 上一次整理工作给 31 篇笔记中没有改过的 21 篇留下了永久性的"这个改过了"警告。总是错的警告，一旦出现就没人再看。

`llmw read <path> --full` 不受影响——它只打印笔记本身，不显示其他的，因为那份文字会被用来做细致的编辑。

## 2. 替换一个旧的决定时，一条命令就能标记好

要是新笔记推翻了旧笔记，写新笔记的时候加上 `--supersedes`：

```bash
llmw write wiki/decisions/retry-in-the-uploader.md \
  --reason "the uploader owns retries now" \
  --supersedes wiki/decisions/retry-in-the-client.md --stdin
```

旧笔记会被标记成 `status: superseded`，并指向新笔记，搜索时会在路径旁边显示这个：

```
1. wiki/decisions/retry-in-the-client.md [superseded -> wiki/decisions/retry-in-the-uploader.md]
```

新旧笔记都会被备份并记录在日志里，如果你指定的笔记不存在，就什么都不会被写。

这样做成一条命令而不是两条的原因是：写新笔记是人们会记得的事，标记旧笔记就是人们容易忘的事。一篇笔记被推翻了好几个月，仍然标记着"活跃"，这就是后来做出错误决定的原因。

旧笔记保留它的内容。被推翻的决定仍然解释了它当初*为什么*被做出来了，这个理由通常比决定本身活得更久——所以被标记为已取代的笔记，是被标记而不是隐藏或排到后面去。

## 3. 笔记可以说出它描述的是哪些文件

在笔记的前言里加一个 `code:` 列表：

```yaml
---
title: Retry budget moves into the uploader
type: decision
status: active
created: 2026-08-31
updated: 2026-08-31
code:
  - src/uploader.py
  - src/retry.py
---
```

然后，AI 在改完其中某个文件的那一轮结束的时候，结束提示会列出这篇笔记：

```
Source changed: record durable knowledge with `llmw write`/`edit`/`patch`...
Pages describing what changed: wiki/decisions/retry-budget.md
```

这就是"记得更新 wiki"和"这篇具体的笔记就是讲你刚改的文件的"之间的区别。改代码那一刻 AI 对这个改动的记忆是最清新的，也只有在那个时候改笔记才容易。

这些路径是相对于你项目文件夹的。它们不是链接——一篇列了 `src/uploader.py` 的笔记不会因为链接坏了而被报告，`llmw lint` 也不会为这些路径抱怨。

## 小小的提醒，在你写笔记的时候

`llmw write`、`edit` 和 `patch` 会在以下情况下打印一条简短的提醒（输出到错误流，所以永远不会混进别人在读的输出里）：

- 笔记缺少你项目要求的前言字段，或者
- 你改了笔记的内容但没改 `updated` 日期。

这两种情况都不会阻止写入。它们是提醒，不是规则——你可能只是在修复一个拼写错误，那样的话就没有什么需要重新陈述的。如果笔记已经在今天更新过了，第二种情况保持沉默。

**`updated` 永远不会被自动改。** 要是它被改的话，修复一个拼写错误就会让一篇过时的笔记看起来新鲜出炉——而一篇看起来比实际更新的笔记，正好会导致这整个功能存在的目的相反的结果。一篇看起来*比实际更旧*的笔记只是会让你多花一点时间查一下代码。拿不准的时候，显示应该让你对笔记的信任度*降低*，而不是提高。

## 为什么它不干脆直接检查代码

最显而易见的想法是，把每篇笔记跟版本控制里的文件比一下，标记出那些代码改得比笔记更新的。这个想法曾经在这个项目自己的 wiki 上被实现并测试过，但不管用：**24 篇笔记里有 17 篇被标记**，几乎全是因为一次只是把导入语句挪了位置的重构，改动的意思其实一点没变。

只看单个函数也改不了这一点——那次重构确实编辑了笔记里提到的函数的内部。根本原因其实很简单：一个文件改动不是"讲它的那句话变成假的"的证据。改名字、拆分函数、整理导入——这些都会触发检查，但都不会让笔记错。

一个错两次的检查就会被忽视，一旦被忽视了，就比什么都没有还坏，因为它让 wiki 看起来像被监管过似的，实际上没有。所以 `llmw` 只是把日期告诉你让你自己判断，标记上有人明确说被替换的东西，还有指向那些说它们是讲你刚改文件的笔记。这三种方法都是它真的知道的。
