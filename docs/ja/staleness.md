# メモが古くなるのを防ぐ

[English](../en/staleness.md) · [한국어](../ko/staleness.md) · **日本語** · [简体中文](../zh-Hans/staleness.md) · [Español](../es/staleness.md) · [Français](../fr/staleness.md)

一番役に立つメモというのは、「どのファイルがどの関数を呼んでいるのか、その順番は」といった、実際のコードの仕組みを説明しているものです。ところが同時に、そうしたメモほど時間がたつと正確さを失いやすいのです。コードは動き続けているのに、メモは止まったままですから。

問題は「メモが古くなる」ことそのものではなく、古いメモが新しいメモと見分けがつかないという点です。AIがそれを読んで信じ込み、数週間前から通用しなくなった情報に基づいて判断してしまう。これはメモがないよりも悪いことです。

`llmw` は、どのメモが古くなったかを推し量ろうとはしません。その理由は
[なぜコードをチェックするだけではうまくいかないのか](#なぜコードをチェックするだけではうまくいかないのか)
のセクションを見てください。その代わり、より単純な3つのことをします。

## 1. 検索と読み込みで、メモの情報がどのくらい古いかを教える

検索結果には、メモのタイトルと、最後に更新された日時が表示されるようになりました。

```
1. wiki/decisions/retry-budget.md
   title: Retry budget moves into the uploader (v0.1.18)
   updated: 2026-07-13 (49d ago)
   summary: ...
```

ディスク上のファイルが、メモの日付より新しい場合は、両方の日時が表示されます。

```
   updated: 2026-07-13 (49d ago, file modified 2026-08-31)
```

この差は、誰かがメモの本文を編集したのに、その日付を更新し忘れたということです。つまり、メモがその日付より新しい内容を説明しているかもしれませんし、逆かもしれません。両方の数字を表示するのは意図的なものです。どちらか一方だけを選ぶと、「最後にこのファイルを誰かが触った日」が「最後に誰かがこれが本当だと確認した日」にすり替わってしまい、このふたつは全く別のものだからです。

`llmw read <path> --full` は特別です。メモと何もほかに出力しません。そのテキストそのものが、慎重な編集作業に使われるからです。

## 2. 古い決め事を置き換えるときは、一度のコマンドで整理する

新しいメモが古い決め事を覆すときは、`--supersedes` を付けて書きます。

```bash
llmw write wiki/decisions/retry-in-the-uploader.md \
  --reason "the uploader owns retries now" \
  --supersedes wiki/decisions/retry-in-the-client.md --stdin
```

古いメモは `status: superseded` と付けられ、新しいメモへのポインタが書き込まれ、検索結果では置き換え先が表示されます。

```
1. wiki/decisions/retry-in-the-client.md [superseded -> wiki/decisions/retry-in-the-uploader.md]
```

古い方のメモも新しい方のメモも、バックアップが取られてログに記録されます。指定したメモが実在しなければ、何も書き込まれません。

このやり方が2つのコマンドではなく1つなのは理由があります。新しいメモを書き込むのは覚えていても、古いメモを戻して整理するのは忘れるからです。置き換えられてから何ヶ月もたったのに「有効(active)」のままのメモは、あとで間違った判断につながる原因になります。

古いメモの本文は残ります。置き換えられた決め事も、*なぜそう決めたのか*という根拠は説明の価値があり、その根拠はたいていその決め事そのものより長く活躍します。だから古いメモは隠したり検索結果を下げたりするのではなく、マークして残すのです。

## 3. メモは、自分が説明しているファイルを記載できる

メモの frontmatter に `code:` リストを追加してください。

```yaml
---
title: Retry budget moves into the uploader
type: decision
status: active
created: 2026-08-31
updated: 2026-08-31
code:
  - src/uploader.py
  - src/retry.py
---
```

こうすると、AIがその中のファイルを編集して今回のターンが終わるとき、ターン終了時の案内に、そのメモが名前で表示されるようになります。

```
Source changed: record durable knowledge with `llmw write`/`edit`/`patch`...
Pages describing what changed: wiki/decisions/retry-budget.md
```

「wikiを更新することを忘れないで」と「このメモはあなたが今編集したファイルについて書いたものです」では大違いです。AIはその変更がまだ頭に新しいので、そのタイミングでメモを更新するのはコストが低いのです。

これらのパスは、プロジェクトフォルダからの相対パスです。これはリンクではありません。あるメモが `src/uploader.py` を記載していても、リンク切れとは報告されませんし、`llmw lint` が文句を言うこともありません。

## 書くときの小さな案内

`llmw write`、`edit`、`patch` は、次の場合に短い案内を出力します(エラーストリームに出すので、他が読んでいるアウトプットに混じりません)。

- あるメモが、プロジェクトが必須としてる frontmatter フィールドを欠いている、または
- メモの本文を編集したのに、`updated` の日付をそのままにしている

どちらも書き込みを止めません。ルールではなく、ただの案内です。タイポを直しているだけかもしれませんから、その場合は言い直す必要はありません。2番目の案内は、そのメモをすでに今日中に更新していれば、黙ったままです。

**`updated` は自動では変わりません。** もし自動で変わったら、タイポを直すだけでも古いメモが新しく見えてしまいます。新しく見えるメモは、この機能全体が存在する理由である「間違った判断」につながります。メモが実際より*古く*見える方が、単にコードを見直すだけでいいので、まだマシです。疑わしいときは、表示はメモを*信じにくく*させるべきで、信じやすくさせるべきではありません。

## なぜコードをチェックするだけではうまくいかないのか

よくある考え方は、各メモとバージョン管理されているファイルを比べて、メモの対象ファイルの方が最近変わっていたら、そのメモにフラグを立てるというものです。これはこのプロジェクト自身のwikiで実装して測定してみましたが、うまくいきませんでした。**24個のメモのうち17個にフラグが立ってしまいました**。ほぼ全部、たった1つのリファクタリングが原因です。インポート文を移動させただけで、意味のある変更は何もなかったのです。

個別の関数まで絞ってみても、同じのことになります。その同じリファクタリングが、メモが指す関数の内部まで本当に編集してしまったからです。根本的な理由はシンプルです。ファイルが変わることは、そのファイルについての文が偽になったことの証拠にはならないのです。変数名を付け替えたり、関数を分割したり、インポート文をきれいにしたり — どれもチェックを引っ掛かりますが、どれもメモを間違わせません。

2度に1度間違う検査は無視されてしまい、いったん無視されるようになると、wikiが監視されているように見えるのに実際は違うということになるので、むしろなす術もなくなります。だから `llmw` は日付を見せて、あなたに判断させ、誰かが明確に置き換わったと言ったものをマークし、あなたが今さっき触ったファイルについて言及しているメモを指し示します。この3つはすべて、`llmw` が実際に知ることができることです。
